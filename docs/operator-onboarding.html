1계정 발급 절차

운영 콘솔(admin/*.html)은 Supabase Auth 계정 + app_metadata.role = "operator"로만 들어갈 수 있습니다. 콘솔 화면 자체에는 계정을 추가·삭제하는 기능이 없습니다(settings.html#ops는 조회 전용).

  1. 기존 운영자나 개발 담당에게 이메일 주소를 알려 계정 생성을 요청합니다.
  2. Supabase 대시보드(또는 개발 담당의 Admin REST 호출)로 계정이 만들어지고, app_metadata.role = "operator"가 부여됩니다. 이 값이 없으면 로그인은 되어도 "운영자 권한이 있는 계정으로 로그인해 주세요" 메시지와 함께 즉시 로그아웃됩니다.
  3. 임시 비밀번호(또는 초대 메일)를 전달받아 admin/index.html에서 첫 로그인을 합니다.
  4. 로그인 직후 dashboard.html 상단의 "기준 시각"이 지금 시각과 맞는지 한 번 확인합니다 — 실제 서비스 계정이라면 데모 고정 시각(2026-10-08 19:30)이 아니라 현재 시각이 보입니다.
  5. 비밀번호를 본인만 아는 값으로 바꿉니다(계정 설정 경로는 회원용 ko/account.html과 별개로, 운영자 비밀번호 변경은 Supabase Auth 표준 절차를 따릅니다).
콘솔 접근 권한과 별개로, 실제 응대(이메일 발신, 전화)에 쓸 운영 대표 메일 주소와 VOC 접수함 접근 권한도 이 시점에 함께 받아 둡니다.

2콘솔 둘러보기

좌측 메뉴 순서 그대로입니다. 처음 며칠은 이 순서대로 한 번씩 눌러 보는 것을 권합니다.

메뉴무엇을 하는 화면인가한 줄 요약
대시보드오늘 할 일 목록(SLA 초과·임박, 새 접수, 마감 임박, 취합중 검토, 파트너 심사 지연, 발송 실패)과 상태 분포, 회원 카드, 최근 이력을 한 화면에 모아 보여줍니다.하루의 시작은 항상 여기입니다.
견적 요청 목록/상세전체 요청을 리스트·칸반으로 보고, 상세 화면에서 상태 전이·초대·재초대·라운드·선정·이력을 다룹니다.실제 업무 시간의 대부분을 쓰는 화면입니다.
호텔 파트너 목록/상세파트너 신청 심사(승인·거절·중지·재승인)와 초대 이력, 응답 통계를 봅니다.신청 후 5영업일 기한을 여기서 관리합니다.
회원 목록/상세여행사·기업 담당자 계정 상태를 보고 잠금 해제·정지·이관·연결 요청 승인·탈퇴 처리를 합니다.모든 조치에 사유를 남겨야 합니다.
피드백의견 보내기·문의 폼으로 들어온 VOC를 분류·배정·상태 전이하고 메모를 남깁니다.일일 트리아지(10:00·16:00)를 여기서 합니다.
설정영업일·공휴일, 기본 규칙(읽기 전용), 알림 템플릿·발송 로그, 운영자 계정, 시스템 상태(크론·시크릿), 전제 조건 체크리스트 6개 탭입니다.공휴일 입력을 잊으면 SLA 계산이 틀어집니다.

대시보드의 "오늘 할 일" 카드 순서를 그대로 하루 흐름으로 씁니다(admin.js의 A.todo() 정의 순서).

  2. SLA·초대 기한 초과 (빨강) — 있으면 최우선. 오늘 안에 오거나이저에게 진행 상황을 회신합니다.
  3. SLA·초대 기한 임박 (1영업일 이내, 노랑) — 검증중이면 오늘 오픈까지, 오픈 상태면 오늘 초대까지 끝냅니다.
  4. 새 접수 — 받은 당일 검증중으로 넘깁니다. 이 전이가 SLA 기산점이므로 미루면 안 됩니다.
  5. 마감 24시간 이내 · 제출 0건 — 미응답 호텔에 전화나 개인 메일로 팔로업합니다.
  6. 피드백 트리아지 10:00 — admin/feedback.html에서 신규 건에 우선순위·하위 코드를 매깁니다(VOC SOP).
  7. 취합중 검토 — 마감된 요청의 비교표를 확인하고 당일 전달합니다. 통화가 섞였으면 USD 참고환산부터 확인합니다.
  8. 초대·재초대 — 오픈 상태 요청에 파트너를 초대하거나, 마감이 바뀐 초대를 재초대합니다.
  9. 파트너 심사 지연 — 5영업일이 지난 신청을 오늘 심사합니다.
  10. 발송 실패 — 수신 주소를 확인하고 직접 메일로 대신 보낸 뒤 "직접 보냄"으로 표시합니다.
  11. 피드백 트리아지 16:00 — 오후에 들어온 건을 다시 한번 분류합니다(일일 2회 트리아지).

5절대 하지 말 것

  • 공유 링크로 선정 처리하기 — 공유 링크(?s=)는 보기 전용입니다. 서버가 선택 요청 자체를 거부하므로 시도해도 안 되지만, 오거나이저에게 "공유 링크로도 고를 수 있다"고 안내하지 않습니다. 선택은 요청 소유 회원(또는 비회원 접수자) 본인만, 본인 연락처로 받은 추적 링크에서만 할 수 있습니다.
  • 인증 없이 성사 처리하고 넘어가기 — 백엔드 연결 전 과도기에 운영자가 오거나이저의 이메일 회신만 보고 콘솔에서 대신 닫는 경우, 인증 기록이 없다는 사실이 요청 상세에 그대로 남습니다. 확인 없이 습관적으로 대신 닫지 않습니다 — 반드시 오거나이저 본인 확인(전화 등) 후 처리합니다.
  • 예산을 호텔에 노출하기 — 오거나이저 정보(회사명·담당자·연락처·예산)는 "호텔에 보이지 않음" 배지가 붙은 영역입니다. 요건서 메모나 안내 메일에 예산·회사명·개인 이름을 옮겨 적지 않습니다(익명화 검토 항목).
  • 호텔 직접 연락처를 오거나이저에게(또는 그 반대로) 미리 전달하기 — 연락처 교환은 성사 시점의 연결 메일(HTL_SELECTED_CONNECT)로만 이루어집니다. 진행 중에 "미리 연결해 달라"는 요청이 와도 콘솔 밖에서 개별적으로 연락처를 넘기지 않습니다.
  • 상태를 되돌리거나 SQL로 직접 바꾸기 — 종료 상태(반려됨·성사·미성사·취소)에서 나가는 전이는 없고, 콘솔에 없는 버튼을 DB로 우회해 만들지 않습니다. 실수는 되돌리기가 아니라 뒤이은 절차(설명·이관·사람 개입)로 수습합니다 — 장애 대응 runbook #12 참고.

6자주 하는 작업 7가지

화면 이름과 버튼 문구는 실제 콘솔 그대로입니다.

1. 새 접수를 검증중으로 넘기기

  1. 대시보드 → "새 접수" 카드 클릭 (또는 견적 요청 목록에서 received 필터)
  2. 해당 요청을 열어 견적 요청 상세로 이동
  3. "상태 전이" 섹션에서 「검증중(으)로」 클릭 — 가드 조건 없음, 이 순간이 SLA 기산점입니다

2. 검증 후 오픈으로 전이하기(익명화 검토)

  1. 견적 요청 상세 → "익명화 검토" 섹션에서 원문 메모 중 회사명·사람 이름·전화·이메일·금액·"예산" 표현이 없는지 확인
  2. 문제 없으면 「익명화 검토 완료 표시」 클릭
  3. "상태 전이"에서 「오픈(으)로」 클릭 — 완료 표시가 없으면 버튼이 막힙니다

3. 호텔 초대해서 비딩 시작하기

  1. 견적 요청 상세 → "마감 · 초대" 섹션에서 마감일시를 정하고 승인 파트너 목록에서 초대할 호텔을 고름
  2. 「초대 보내기」 클릭 — 초대가 2곳 미만이면 "오거나이저에게 미리 알리셨나요?" 확인 창이 뜹니다
  3. "상태 전이"에서 「비딩중(으)로」 클릭 (마감·초대 1곳 이상이 이미 충족되어 있으면 자동으로 넘어가는 화면 흐름을 따릅니다)

4. 마감이 바뀐 호텔을 재초대하기

  1. 요청 마감을 바꾸면 "이미 보낸 초대의 마감은 바뀌지 않습니다" 확인 창이 뜹니다 — 확인
  2. "초대 현황" 표에서 마감이 요청 마감과 달라진 행에 나타난 「재초대」 클릭
  3. 이전 초대 행은 재초대됨으로 이력에 남고, 새 마감의 새 초대 행이 생깁니다

5. 취합중 요청을 비교표로 정리해 전달하기

  1. 견적 요청 상세 → "비교표" 섹션에서 제안 A·B·C를 확인
  2. 통화가 2종 이상 섞였으면 모든 견적에 USD 참고(트윈)와 기준일을 입력
  3. "상태 전이"에서 「전달됨(으)로」 클릭 — 제출 견적 1건 이상이 조건입니다

6. 호텔 파트너 신청 심사하기

  1. 호텔 파트너 목록에서 pending(신청) 또는 지연 배지가 붙은 건을 열기
  2. "심사 체크리스트"로 해외 소재·단체 50명 이상 수용·담당자 연락처 확인 여부를 봄(볼룸 유무는 승인 조건이 아님)
  3. 조건 충족 시 「승인」, 미충족 시 사유를 적고 「거절」 — 결과 메일은 시스템이 자동 발송합니다

7. 회원 연결 요청을 확인해 승인하기

  1. 회원 상세 → "연결 요청" 섹션에서 대기 중인 건 확인(휴대전화만 같아 자동 연결되지 않은 경우)
  2. 같은 회원이 맞는지 확인 후 「승인」 또는 「거절」 클릭
  3. 승인하면 ACC_LINKED가 발송되고 비회원 요청이 이 회원 소유로 연결됩니다

7용어집

오거나이저·호텔·콘솔 화면에서 같은 개념을 다르게 부르는 경우가 있어, 콘솔 기준 용어로 통일했습니다.

요청 (RFP)
오거나이저가 접수한 견적 요청 1건. 접수됨부터 성사·미성사·반려됨·취소까지의 생애주기를 가집니다.
요건서
요청 내용을 정리해 호텔에 보여 주는 문서 형태. 오거나이저 정보(회사명·예산 등)는 빠진 익명화된 버전입니다.
제안
호텔이 제출한 견적 1건. 비교표에는 도착 순서대로 A, B, C로 표시됩니다.
라운드
같은 요청 안에서 조건을 바꿔 다시 비딩하는 차수. 처음은 라운드 1이고, "조건 변경 → 새 라운드"를 쓸 때마다 1씩 올라갑니다.
초대
호텔 한 곳이 한 라운드에서 받는 요청 단위. 초대·열람·제출·거절·마감·재초대됨 상태를 가집니다.
재초대
새 마감으로 같은 호텔을 다시 초대하는 것. 이전 초대는 재초대됨으로 이력에 남고 새 링크가 발급됩니다.
선정
전달됨 상태에서 오거나이저가 고른 호텔 1곳에 붙는 표시. 성사 전이의 조건(정확히 1곳)입니다.
연결
성사 시점에 선정 호텔과 오거나이저의 연락처가 서로 전달되는 것(HTL_SELECTED_CONNECT 메일).
공유 링크
요청 소유 회원이 동료에게 보내는 보기 전용 링크(?s=). 진행 상황과 비교표만 보이고 선택·조건 변경은 할 수 없습니다.
성사
선정 호텔 1곳이 정해져 요청이 닫힌 종료 상태.
미성사
선택하지 않음·유효기한 경과·두 차례 요청에도 제안 없음으로 요청이 닫힌 종료 상태.

8알림이 언제 누구에게 가는지

전체 문안·변수는 알림 라이브러리에 있습니다. 여기서는 "누가 받는지"만 빠르게 찾을 수 있게 정리했습니다.

알림ID받는 사람채널자동/수동
접수 확인ORG_RECEIVED오거나이저알림톡+이메일자동

9문의 응대 원칙

VOC SOP(프로젝트 문서 micego-voc-sop-cx-v1) 요약입니다. 전체 템플릿 문구는 원본 문서를 봅니다.

구분기준
일일 트리아지영업일 10:00, 16:00 — 신규(new) 건을 분류(triaged)합니다.
주간 정리월요일 11:00 — 보류(on_hold)와 오래된 건을 다시 봅니다.
착수 기한P1은 접수 4영업시간 안, P2는 1영업일 안에 착수(in_progress)합니다.
분류 기한신규 건은 1영업일 안에 분류합니다. 넘기면 콘솔에 "분류 지연" 배지가 붙습니다.
답변 템플릿1차 답변(②), 처리 완료 안내(③), 반영 안 함 안내(④) 세 종류가 있고, 원본 알림 메일에 그대로 답장해 접수번호(FB-YYMMDD-XXXX)를 유지합니다.

템플릿 위치

템플릿 문구는 콘솔 안이 아니라 VOC SOP 문서(프로젝트 문서함의 micego-voc-sop-cx-v1) §9.7에 있습니다. 콘솔의 admin/feedback-detail.html은 분류·상태·메모만 다루고, 실제 답장은 운영팀 메일함(FEEDBACK_INBOX)에서 알림 메일에 직접 답장하는 방식입니다.

우선순위와 하위 코드를 매기지 않으면(ETC 제외) 상태를 분류됨으로 넘길 수 없습니다(GUARD_TRIAGE_FIELDS). 보류로 돌릴 때도 사유 메모가 필수입니다(GUARD_HOLD_NOTE).

10도움 요청 경로

  • 콘솔 사용법이 헷갈릴 때 — 이 문서와 상태전이표 v1.7을 먼저 확인합니다. 화면 문구·가드 조건은 상태전이표 §2~§5-4에 전부 있습니다.
  • 화면이 안 되거나 오류가 뜰 때 — 장애 대응 runbook의 심각도 정의부터 확인하고, 판단이 서면 해당 시나리오 카드를 따라갑니다. 애매하면 낮추지 말고 개발 담당에게 바로 공유합니다.
  • 사유·조건이 기억 안 나는 조치(사유 필수인 전이 등) — admin/settings.html "기본 규칙"·"회원 인증 규칙" 탭이 읽기 전용 참고표입니다.
  • 그래도 모르겠을 때 — 계정을 발급해 준 운영자나 개발 담당에게 요청번호·회원 ID·화면 캡처와 함께 물어봅니다. 혼자 SQL로 고치려 하지 않습니다(절대 하지 말 것 참고).
