# MICEGO 운영 SOP v2.2 부록 — 피드백·VOC 처리 SOP + CX 응대 - 클로드

v1.0 · 2026-09-27 · 적용 대상: 운영 SOP v2.1(상태전이 기준)에 §9 "피드백·VOC"로 추가. 기존 절은 변경 없음.

## 9.1 창구와 흐름

- **창구** — 사이트 모든 페이지의 우하단 "의견 보내기(Feedback)" 버튼과 ko/en 문의 페이지. 두 창구 모두 같은 `feedback` 테이블에 쌓이고, 운영 알림 메일(`FEEDBACK_INBOX`)로 한 통씩 들어온다.
- **자동 첨부** — 페이지 경로, 화면 상태(track/bid 상태·미리보기 여부), 요청번호(MG-…), 접속 링크 해시(원문 없음), 브라우저·화면 크기, 최근 JS 오류 3건, 빌드 버전. IP는 저장하지 않는다.
- **접수번호** — `FB-YYMMDD-XXXX`. 메일 제목·콘솔·접수자 확인 메일에 같은 번호가 붙는다. **답장할 때 제목의 접수번호를 지우지 않는다.**
- **답변 경로** — 운영자가 메일함에서 알림 메일에 직접 답장(Reply-To가 접수자). 콘솔은 상태·분류·메모만 관리한다.
- **스테이징·의심 건** — DEMO(스테이징)와 스팸 의심 건은 저장만 되고 알림이 오지 않는다. 콘솔에서 "DEMO 포함", "의심만" 필터로 본다.

## 9.2 유형 분류

| 대분류 | 하위 코드 | 뜻 | 기본 담당 |
|---|---|---|---|
| SYS 화면·기능 | BUG 오류 신고 | 동작하지 않음, 잘못된 값, 깨진 화면 | FE/BE |
| | IDEA 개선 제안 | 기능·흐름 제안 | 기획 |
| | TEXT 표시·번역 | 문구·번역·표기 오류 | 운영 |
| OPS 견적·운영 | RFP 견적·RFP | 요청 내용·진행·초대 관련 | 운영 |
| | BID 비딩·조건 | 호텔의 견적 제출·조건 문의 | 운영 |
| | ACCT 계정·회원 | 가입·로그인·정보 변경 | 운영 |
| | PARTNER 파트너 등록 | 호텔 파트너 신청·심사 | 운영 |
| | POLICY 정책·약관 | 수수료·약관·개인정보 | 운영+법무 |
| ETC 기타 | (없음) | 칭찬·일반 의견·범위 밖 | 운영 |

유저는 대분류만 고른다. 하위 코드는 트리아지 때 운영자가 붙이며, 대분류가 틀렸으면 고쳐도 된다.

## 9.3 우선순위와 착수 기준

| P | 정의 | 착수(처리 중) 기한 | 답변 기한 |
|---|---|---|---|
| P1 | 견적 요청·비딩 제출·제안 선정·인증번호처럼 **핵심 흐름이 막힘**, 개인정보 노출 의심, 여러 사용자에게 영향 | 알림 즉시, 4영업시간 이내 | 당일 1차 답변 |
| P2 | 기능 오류지만 우회 가능, 특정 요청의 진행이 늦어질 우려, 진행 중 RFP 관련 문의 | 1영업일 | 1영업일 |
| P3 | 사소한 오류·문구·번역, 작은 개선, 일반 문의 | 주간 정리에서 배정 | 3영업일 |
| P4 | 아이디어·참고·칭찬·중복 | 주간 정리에서 검토 | 접수 확인 메일로 갈음 |

콘솔은 P1 미착수 4시간, P2 미착수 1영업일, 신규 미분류 1영업일이 넘으면 "지연" 배지를 띄운다.

## 9.4 상태와 전이 규칙

`신규 → 분류됨 → 처리 중 → 완료` / `보류` / `다시 열기`

| 전이 | 조건(콘솔이 강제) |
|---|---|
| 신규 → 분류됨 | 우선순위 + 하위 코드(ETC 제외) 지정 |
| 신규 → 완료 | 스팸·중복·조치 없음만 가능 |
| 분류됨 → 처리 중 | 담당자 지정 |
| 분류됨·처리 중 → 보류 | 보류 사유 메모 필수 |
| → 완료 | 처리 결과 필수(수정 완료·답변 완료·반영 안 함·중복·스팸·조치 없음) |
| 완료 → 처리 중 | 다시 여는 사유 메모 필수 |

완료 처리 뒤 "답변 발송 여부"는 메모에 남긴다(예: "10/08 19:40 메일 회신"). 회신 이메일이 없는 건은 답변 없이 완료한다.

## 9.5 일일 트리아지 (영업일 10:00 · 16:00)

1. 콘솔 > 피드백 목록(기본 필터: 신규·분류됨·처리 중·보류, DEMO 제외)에서 **신규** 건을 연다.
2. 본문과 컨텍스트 패널을 읽고 대분류 확인 → 하위 코드 → 우선순위 → 담당을 지정한다. "연결 요청" 배지가 **빨강(불일치)**이면 요청번호와 링크 중 어느 쪽이 맞는지 본문으로 판단하고 메모에 남긴다.
3. "분류 완료"를 누른다. P1이면 곧바로 담당 지정 후 "처리 시작"하고 접수자에게 1차 답장(9.7 템플릿 ②)을 보낸다.
4. 답변이 필요한 건(OPS 전부, SYS-BUG)은 메일함에서 접수번호로 검색해 답장한다. 답장 후 콘솔 메모에 "회신 완료 + 요지"를 남긴다.
5. **알림 실패** 배지가 있으면 상세에서 "알림 다시 보내기". 반복되면 Resend 대시보드와 발신 도메인 상태를 확인한다.
6. 스팸·중복은 "바로 종료"로 닫는다. 같은 사람이 같은 내용을 여러 번 보냈으면 최신 건만 남기고 나머지는 중복 처리한다.

## 9.6 주간 정리 (매주 월 11:00, 30분)

1. 콘솔 "프리셋: 주간 정리"(보류 전체 + 지난주 완료 + 7일 넘은 신규)를 연다.
2. 지난주 접수 건을 하위 코드별로 센다(CSV 내보내기 → 시트). **같은 하위 코드·같은 페이지에서 3건 이상**이면 개선 백로그로 승격하고, 각 건 메모에 백로그 번호를 적는다.
3. 보류 건은 재검토일이 지났는지 본다. 지났으면 다시 진행하거나 "반영 안 함"으로 닫고 접수자에게 알린다.
4. 7일 넘은 신규가 있으면 그 자리에서 분류한다(있으면 안 되는 상태).
5. 백로그가 릴리스되면 관련 건을 "수정 완료"로 닫고, 회신 이메일이 있는 접수자에게 처리 완료 메일(9.7 ③)을 보낸다.
6. 주간 숫자(접수·완료·평균 착수 시간·P1 건수)를 운영 회의 노트에 한 줄로 남긴다.

## 9.7 CX 응대 원칙과 템플릿

**원칙**
- 첫 응답은 1영업일 안에. 조치가 끝나지 않았어도 "확인 중이며 언제까지 알려드리겠다"를 먼저 보낸다.
- 재현한 것과 못 한 것을 사실대로 쓴다. 추정은 추정이라고 밝힌다.
- 약속한 기한을 못 지키면 기한 전에 먼저 알린다.
- 호텔(영어)에는 사이트 화면과 같은 용어(Request, Quote, Deadline, Selected)를 쓴다.
- 요청 상세(다른 호텔의 금액, 오거나이저 신원)는 답장에 담지 않는다. 신원 공개 시점 정책(약관)을 따른다.
- 답장 제목의 접수번호(FB-…)는 그대로 둔다. 새 스레드를 만들지 않는다.

**① 접수 확인(자동 발송, 수정 불필요)**
- ko 제목 `[MICEGO] 보내 주신 의견을 접수했습니다 (FB-…)` / en `[MICEGO] We've received your feedback (FB-…)`
- 본문에 접수번호·유형·시각만 담고 사용자가 쓴 내용은 넣지 않는다(스팸 중계 방지).

**② 1차 답변 / 확인 중**

ko
```
안녕하세요, MICEGO 운영팀입니다. (접수번호 {REF})

보내 주신 {요약}에 대해 확인했습니다.
{확인한 사실 / 재현 여부}
{조치 내용 또는 "원인을 확인 중이며 {날짜} 안에 다시 안내드리겠습니다."}

추가로 알려 주실 내용이 있으면 이 메일에 그대로 답장해 주세요.
```
en
```
Hello, this is the MICEGO team. (Reference {REF})

We've looked into {summary}.
{what we found / whether we could reproduce it}
{action taken, or "We're still investigating and will update you by {date}."}

If there's anything to add, just reply to this email.
```

**③ 처리 완료 / 반영 안내**

ko
```
안녕하세요, MICEGO 운영팀입니다. (접수번호 {REF})

알려 주신 {항목}이 {날짜}에 반영되었습니다.
{바뀐 점 한 줄}

소중한 의견 감사합니다. 같은 문제가 다시 보이면 이 메일에 답장해 주세요.
```
en
```
Hello, this is the MICEGO team. (Reference {REF})

The issue you reported ({item}) was resolved on {date}.
{one line on what changed}

Thank you for helping us improve. If it comes back, reply to this email.
```

**④ 반영하지 않기로 한 경우(보류 종료·반영 안 함)**

ko
```
안녕하세요, MICEGO 운영팀입니다. (접수번호 {REF})

제안해 주신 {항목}은 검토했지만 지금은 반영하지 않기로 했습니다.
이유: {한 줄}
{대안이 있으면 한 줄}

의견은 기록해 두고 다음 개편 때 다시 살펴보겠습니다. 감사합니다.
```
en
```
Hello, this is the MICEGO team. (Reference {REF})

We reviewed your suggestion ({item}) but won't be making this change for now.
Reason: {one line}
{alternative, if any}

We've kept your feedback on file for future updates. Thank you.
```

**⑤ 비딩·요청 관련 문의(호텔·오거나이저 공통 뼈대)**

- 진행 상태를 사이트 표기와 같은 단어로 알려 준다("현재 '견적 취합 중'이며 마감은 10/10 18:00 KST입니다").
- 상대방이 해야 할 일이 있으면 링크 대신 "받으신 메일의 버튼"으로 안내한다(피싱 오해 방지).
- 다른 호텔의 조건·금액·이름은 언급하지 않는다.

## 9.8 개인정보·보안 운영 규칙

- 회신 이메일은 동의를 받은 것만 저장되며 12개월 뒤 자동 익명화된다. 답장 메일함의 스레드도 12개월 지나면 정리한다.
- 접수 본문에 접속 링크(토큰)가 붙어 오면 서버가 `[token]`으로 가린다. 메일함에 원문이 남아 있으면 그 메일은 삭제한다.
- 운영자 역할 회수 뒤에도 최대 1시간은 콘솔 권한이 남는다. 즉시 차단이 필요하면 Supabase에서 세션을 강제 종료한다.
- 알림 메일이 하루 150건을 넘으면 "상한 도달" 메일 한 통만 오고 나머지는 콘솔에서 본다. 이 경우 공격 가능성을 먼저 의심한다.
